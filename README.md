# О проекте

Бэкенд для приема лид-форм и отправки их в различные приемники: PostgreSQL, Telegram, email и другие адаптеры. В
монорепе также лежит минимальный пример фронтенда — `apps/frontend`.

## Архитектура

```
  [ Gateway ] ──► [ BullMQ/Redis ] ──► [ Router ]
                                            │
        ┌────────────┬──────────────┬───────┴──────┐
        ▼            ▼              ▼              ▼
     [ DB ]     [ Telegram ]    [ Email ]       [ HTTP ] ──► [ Gateway: Каскад ]
```

## Каскад

HTTP-адаптер позволяет строить цепочки инстансов: в `HTTP_LEAD_DELIVERY_ENDPOINTS` можно указать один или несколько
эндпоинтов `POST /api/v1/leads` на других серверах-инстансах, организовав таким образом каскад.

Каскад может быть полезен для отправки лидов из РФ в Telegram и другие деградировавшие в стране сервисы: входной узел на
российском сервере принимает лид (там же можно его сохранить в БД-адаптере чтобы он точно не потерялся), затем через
HTTP-адаптер лид отправляется на зарубежный инстанс, и оттуда уходит в Telegram.

## Гарантии доставки

Доставка имеет семантику at-least-once: при сбоях система предпочитает доставить лид повторно, чем потерять его.
Источники повторных доставок:

- повтор POST лида клиентом или вышестоящим инстансом каскада;
- ретраи BullMQ (`LEADS_QUEUE_ATTEMPTS` с задержкой `LEADS_QUEUE_BACKOFF`);
- ретраи HTTP-клиента на сетевых ошибках и ответах 429 (`HTTP_CLIENT_RETRY_COUNT`).

BullMQ атомарно ставит задачу в очередь и создаёт маркер дедупликации для пары «id лида + канал».
Повторные запросы с тем же id не создают новую задачу для этого канала в течение `LEADS_DEDUPLICATION_TTL_MS`
(по умолчанию 24 часа). Повторы не продлевают TTL; завершение задачи не снимает маркер раньше срока.

Gateway подтверждает приём только после успешной постановки задач для всех каналов. Если часть операций
завершилась ошибкой, запрос возвращает 503. Повтор с тем же id ставит недостающие задачи; уже принятые задачи
защищены дедупликацией. Повторная обработка одной задачи после сбоя по-прежнему может повторить внешнюю доставку.
В БД повторная вставка дополнительно защищена первичным ключом лида.

При обновлении старые маркеры `leads:dedupe:*` не используются: первый повтор ранее принятого лида может создать
новые задачи. Если Redis уже запускался со старым Compose, перед пересозданием контейнера перенесите его `/data`
в именованный volume: прежнее подключение `/redis-data` не сохраняло эти данные.

## Быстрый запуск

Скопируйте репозиторий

```bash
git clone https://github.com/osipovts/leads-router-monorepo.git
```

Скопируйте `.env.example` в `.env` и настройте проект.

```bash
cd leads-router-monorepo
cp .env.example .env # здесь лежат инфраструктурные переменные - учётные данные, порты
cp apps/gateway/.env.example apps/gateway/.env # лимиты запросов, Swagger, BullMQ
cp apps/router/.env.example apps/router/.env # учётные данные адаптеров (Telegram, PostgreSQL, email)
```

Запустите

```bash
docker compose up --build
```

После запуска будут доступны:

1. Пример фронтенда на [http://localhost:5173](http://localhost:5173)
2. Swagger UI на [http://localhost:3000](http://localhost:3000). Включается переменной `APP_SWAGGER_ENABLE` в
   `apps/gateway/.env`
3. Bull Dashboard на [http://localhost:4000](http://localhost:4000)

`docker-compose.yml` содержит лишь самодостаточную демо-конфигурацию: для полноценного production-использования он не
рекомендуется.

# Фронтенд

`apps/frontend` - минимальное React-приложение (Vite + TS): форма отправки лида на `POST /api/v1/leads` с показом
результата. Порт фронтенда настраивается переменной `FRONTEND_FORWARD_PORT` в корневом `.env` (по умолчанию `5173`).

# Тесты

## Unit-тесты

Команда собирает common и генерирует Prisma Client перед запуском тестов; подключение к БД не требуется.

Запуск unit-тестов:

```
pnpm test:unit # в корне монорепы
```

## E2E-тесты

Запуск e2e-тестов:

```
pnpm test:e2e # в корне монорепы
```
